# 過去バージョンへの対応の設計

- 状態: 設計中
- 日付: 2026-11-20
- 前提: [過去バージョンへの対応の調査](legacy-version-support.md)

---

## 1. 目的

古いバージョンのMinecraftで配布マップを保守し続けている制作者にも、このライブラリを使ってもらう。
その人たちが、自分のバージョンのワールドをそのまま読み書きできるようにする。

---

## 2. 決まったこと

利用者と決めたことは次のとおりである。

- バージョン間の変換はしない。読んだ形式のまま書き戻す
- バージョンは最初に読み込むときに決め、以降の読み書きはその形式で行う。指定にするか自動判別にするかは、設計に任された
- 対象は1.13以降とする。1.13より前（ブロックが数値ID）は扱わない
- 作り方はいまのAPIを保ったまま、中で形式の世代ごとに読み書きを切り替える（3章の案1）

---

## 3. 作り方の候補

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 1（採用） | いまの`Chunk`などのAPIを保ち、中で形式の世代ごとの部品を切り替える | 利用者のコードがバージョンによらず同じになる。26.4のような新しい形式も、部品を1つ足せば済む | いまのクラスの中身を組み替える必要があり、5言語ぶんかかる |
| 2 | 世代ごとに別の型を用意する | 型ごとの実装が素直になる | 利用者が型で場合分けを書く必要がある。APIの数が世代の数×5言語で増える |
| 3 | 元のNBTを持ったまま、操作のたびに世代ごとの関数で解釈する | 解釈した状態を持たずに済む | いまの実装はすでに「元のNBT＋解釈した部分」を持つ作りで、案1とほとんど変わらない |

保守している人が自分のバージョンで同じコードを使えることを重く見て、案1にした。

---

## 4. 目標と、しないこと

### 目標

- 1.13以降のワールドを開き、ブロックの読み書き、セクションの列挙、`level.dat`の読み書き、次元とプレイヤーのファイルへのアクセスができる
- 書き戻したチャンクは読んだときと同じ形式になる。`DataVersion`も読んだ値のまま残す
- 触っていないチャンクとセクションは、元とバイト単位で一致する
- 5言語で同じ入力から同じ出力になる

### しないこと

- バージョン間の変換（ブロック・バイオーム・ブロックエンティティ・エンティティ・アイテム）
- 1.13より前のワールド
- ブロックの定義（既定値やプロパティの一覧）を持つこと（[0004](../adr/0004-defer-heightmap-recalc.md)、[0010](../adr/0010-palette-format-26-3.md)の決定5のまま）
- 新しいチャンクやセクションを作ること（いまと同じ）
- ブロックエンティティ・エンティティ・アイテムの中身の解釈（いまと同じく、生のNBTのまま渡す）
- 開発版（スナップショット）で書かれたチャンクのうち、正式版と形式が違うもの（1.13や1.18の開発途中の形式など）

### 失敗とみなすこと

次のどれかが起きたら、動いていても失敗である。

- 読んだときと違う形式でチャンクを書き出す
- `DataVersion`を書き換える
- 世代の取り違えなどで構造が合わないのに、エラーを出さずに読み進めて誤った値を返す

## 5. 形式の世代

### 5.1 チャンク

チャンクの形式はDataVersionで次の5つの世代に分かれる。境界の値はMinecraftが形式を変えたDataVersionである。

| 世代 | DataVersion | バージョン | このライブラリに関わる違い |
|---|---|---|---|
| C1 | 1519〜2202 | 1.13〜1.14.x | `Level`の中にすべてがある。セクションは`Level.Sections`で、ブロックは`Palette`と`BlockStates`。ビット詰めは値が64bitの境目をまたぐ。バイオームは`Level.Biomes`の`int[256]`（列ごと） |
| C2 | 2203〜2528 | 1.15〜1.15.2 | C1と同じで、バイオームが`int[1024]`（4×4×4ごと） |
| C3 | 2529〜2843 | 1.16〜1.17.x | C2と同じで、ビット詰めが値をまたがない |
| C4 | 2844〜5005 | 1.18〜26.2 | `Level`が無くなり、`sections`などがルートの直下にある。`block_states` / `biomes`のパレット付きコンテナ。パレットの要素は`{Name, Properties}` |
| C5 | 5006以降 | 26.3以降 | パレットの要素が文字列か`{id, properties}`（2.0.0のいまの形式） |

1.17（2681）でエンティティは`entities/`の別のリージョンファイルへ移ったが、このライブラリはエンティティを解釈しないので、世代を分けない。
`Level.Entities`はいまの未知のキーと同じく、そのまま残す。

### 5.2 ワールドの構成と`level.dat`

| 世代 | `level.dat`のDataVersion | 構成 |
|---|---|---|
| L1 | 1519〜4785 | オーバーワールドは直下の`region/`、ネザーは`DIM-1/`、エンドは`DIM1/`。データパックの次元は`dimensions/<名前空間>/<名前>/`。プレイヤーは`playerdata/`。ゲームルールなども`level.dat`の中 |
| L2 | 4786以降 | いまの構成（`dimensions/`、`players/data/`、`data/minecraft/`）。[40](../spec/40-world-layout.md)のとおり |

---

## 6. 世代の決め方

- チャンクの世代はそのチャンクを最初に読んだときに、チャンク自身の`DataVersion`で決める。
  1つのワールドに形式の違うチャンクが混ざりうるため（26.2のワールドを26.3で開いても、行っていない場所のチャンクは26.2の形式のまま残る）
- ワールドの構成と`level.dat`の世代は、ワールドを開いたときに`level.dat`の`DataVersion`で決める
- 決めた世代は`Chunk`と`MinecraftWorld`が持ち続け、書き戻しにも同じ世代を使う
- 利用者は世代を指定して、自動の判別を上書きできる。指定はDataVersionの値で受け取り、そこから世代を引く。
  ワールドを開くときに指定すると、構成と、そのワールドから読むすべてのチャンクに効く
- いちばん新しい世代の上限は設けない。いまと同じく、新しいDataVersionのチャンクはいちばん新しい世代で読む

### 6.1 下限より古いチャンク（設計者の判断）

- 下限（1519）との比較は、指定の有無に関わらず、常にチャンク自身の`DataVersion`で行う。
  指定で世代を上書きしても、読み込みの警告と書き込みの`UNSUPPORTED_DATA_VERSION`は素通りできない
- 指定できる値は1519以上に限る。それ未満を指定したら`INVALID_ARGUMENT`にする
- 1519未満のチャンクはどの世代の部品でも解釈しない。読み込みは`VersionMismatchAction`に従ったうえで、元のNBTだけを持つ。
  ブロックとバイオームのAPIは`UNSUPPORTED_DATA_VERSION`にする。数値IDのチャンクを1.13以降の部品で読むと、ブロックが1つも無いように見えてしまうためである
- 書き戻しは、`allow_foreign_data_version`があるときだけ、読んだNBTをそのまま返す

## 7. 実装の形

### 7.1 世代ごとの部品

チャンクの世代ごとに、次のことを受け持つ部品を1つ用意する。部品はDataVersionから表で引き、バージョンによる分岐をほかの場所に書かない。

- チャンクの本体（ルートか`Level`か）と、セクションの一覧のキー（`sections`か`Sections`か）
- セクションのブロックとバイオームの場所とキー名
- パレットの要素と`BlockState`の変換
- ビット詰めの方式（またぐか、またがないか）と最小のビット幅
- バイオームの持ち方（パレット付きコンテナか、数値の配列か）
- ブロックを置き換えたときに取り除く付随データのキー（C1〜C3は`Level.TileEntities` / `Level.TileTicks` / `Level.LiquidTicks`、C4以降は`block_entities` / `block_ticks` / `fluid_ticks`）
- 高さマップと光源の印の場所（`Level.Heightmaps`と`Level.isLightOn`か、ルートの直下か）
- 生成済みとみなす`Status`の値

ワールドの構成の世代（L1 / L2）も、同じように部品を分ける。

### 7.2 公開APIの変化

いまのAPIは保ち、世代によって意味が変わらないものはそのまま使えるようにする。足すもの・変わるものは次のとおり。

| API | 変化 |
|---|---|
| `Chunk.get_block` / `set_block` / `compact` / `section_ys` / `section` | 全世代で使える |
| `Chunk.get_biome` / `set_biome` | C4以降だけ。C1〜C3では`UNSUPPORTED_FEATURE` |
| `Chunk.get_biome_id` / `set_biome_id`（新規） | C1〜C3だけ。数値のバイオームIDをそのまま読み書きする。C1では`y`を見ない。C4以降では`UNSUPPORTED_FEATURE` |
| `Chunk.min_section_y` | C4以降は`yPos`。C1〜C3は`0` |
| `Chunk.status` / `is_fully_generated` | 世代ごとの`Status`の場所と値で判定する |
| `Chunk.clear_heightmaps` / `invalidate_lighting` | 世代ごとの場所に対して行う。`isLightOn`の無い世代では`UNSUPPORTED_FEATURE` |
| `Chunk`に世代を選んだDataVersionを返す取得子（新規） | 指定で上書きしたときは、その値を返す |
| `BlockState.from_nbt` / `to_nbt` | DataVersionを受け取る引数を足す。省いたらいちばん新しい世代（いまと同じ動き） |
| `ChunkReadOptions` / `WorldOpenOptions` | 世代を指定するDataVersionの項目を足す。既定は自動の判別 |
| `MinecraftWorld.dimension_ids` / `dimension` | L1では`minecraft:overworld`を直下、`minecraft:the_nether`を`DIM-1/`、`minecraft:the_end`を`DIM1/`に当てる。データパックの次元は`dimensions/`から探す |
| `MinecraftWorld.player_ids` / `player` | L1では`playerdata/`を読む |
| `MinecraftWorld.data_file` / `Dimension.data_file` | L1では`<次元のフォルダ>/data/<名前>.dat`を読む |
| `LevelData`の取得子 | L1では`SpawnX` / `SpawnY` / `SpawnZ`、`Difficulty`（数値を名前に直す）、`hardcore`を読む。L1に無い値は`UNSUPPORTED_FEATURE` |
| `MIN_SUPPORTED_DATA_VERSION` | `1519`に下げる |

バイオームの数値IDは名前に直さない。1.16.2以降はデータパックで独自のバイオームを足せるので、固定の表では正しく引けないためである。

### 7.3 ビット詰め

C1とC2のビット詰めは、値が64bitの境目をまたぐ。`BitStorage`にこの方式を足し、世代の部品が選ぶ。
またぐ方式では、`data`の長さは`ceil(要素数 × ビット幅 / 64)`になる。

## 8. 決め直すADR

新しいADRを1つ書き、次の2つを置き換える。

| ADR | いまの決定 | 変えたあと |
|---|---|---|
| [0003](../adr/0003-version-policy.md) | 下限未満は読み込みで警告、書き込みでエラー。下限は形式が変わるたびに上げる | 世代を選んで読み書きする。下限（1519）未満だけを警告・エラーにする。新しい形式が出たら、下限を上げずに世代を足す |
| [0010](../adr/0010-palette-format-26-3.md) | 26.2までの形式は扱わない（決定1） | 26.2までの形式もC4として扱う。決定2〜5はC5の決め事として残す |

0010の理由1が挙げた心配（5言語の分岐、書き出す形式の取り違え）には、次のように答える。

- 世代による分岐は7.1の部品の中だけに書く
- 書き出す形式は読んだときの世代で決まり、利用者が書き出す形式を選ぶ手段は無い
- 世代ごとに実ワールドと合成のテストデータを持ち、5言語で同じ結果になることを確かめる

## 9. 進める順番

それぞれの段階で、リリースできる状態にする。

| 段階 | 中身 | これで扱えるようになるもの |
|---|---|---|
| 1 | 世代を選ぶ作りへの組み替え（挙動は変えない）と、C4のチャンク | 26.3のワールドに残った26.2のチャンク、26.1・26.2のワールド |
| 2 | L1の構成と`level.dat` | 1.18〜1.21.xのワールド |
| 3 | C1〜C3のチャンクと、数値のバイオームのAPI | 1.13〜1.17.xのワールド |

26.4で形式が変わったら、この作りに世代を1つ足して対応する。

## 10. テスト

- 各世代の合成のテストベクタを`spec/tools/build_testdata.py`で作り、適合性検証で5言語の出力が一致することを確かめる
- 各世代の実ワールドを`spec/tools/scan_world.py`で走査し、読み込みと、無変更での書き戻しがバイト単位で一致することを確かめる。走査ツールは世代を扱えるように直す
- 形式の違うチャンクが混ざったワールドで、各チャンクが読んだ形式で書き戻されることを確かめる
- 世代を指定して上書きしたとき、構造が合わなければ`MALFORMED_DATA`になることを確かめる
- 指定で上書きしても、1519未満のチャンクの書き戻しが`UNSUPPORTED_DATA_VERSION`で止まることを確かめる
- 9章の各段階は、足した世代の実ワールドで走査が通るまで完了としない（設計者の判断）。
  `level.dat`のキーのように同じ世代の中で変わりうるものは、手に入る複数のバージョンの実ワールドで確かめる
- 実ワールドはリポジトリに入れない。いまと同じく、個人のセーブデータであるため

---

## 11. 実装する人に任せること

- 世代の部品の型と名前、各言語での置き場所（[0002](../adr/0002-idiomatic-naming.md)に従う）
- 7.2で足すAPIの名前。API対応表と`check_docs_sync.py`に合わせる
- C1〜C3で、パレットが1要素のセクションに`BlockStates`があるかどうか。実ワールドで確かめて、書き戻しが元と一致する方に合わせる
- C1〜C3の`Status`の値と、生成済みとみなす値。実ワールドで確かめる
- `isLightOn`が入ったDataVersion。実ワールドで確かめ、それより前の世代では`invalidate_lighting`を`UNSUPPORTED_FEATURE`にする
- C1〜C3の光源だけのセクション（`Y`が`-1`と`16`）の扱い。いまの「`block_states`を持たないセクション」と同じく、ブロックAPIでは空として扱う
- リリースの版の付け方。古い形式を足すのは機能の追加なので`y`を上げるのが基本だが、`BlockState`の引数の足し方によっては互換性が崩れる。崩れるなら`x`を上げる

---

## 12. 確かめていないこと

- 世代の境界のうち、2203、2529、2844は調査の結果で、このリポジトリでは確かめていない。1.13の正式版のDataVersion（1519）も同じである
- C4（1.18〜26.2）のチャンクの構造が、このライブラリが触る範囲で同じであること。26.1と26.2の実ワールドでは確かめたが、1.18〜1.21.xでは確かめていない
- L1の`level.dat`のキー（`SpawnX`など）。[40](../spec/40-world-layout.md)の「1.21.xからの変更点」に基づく

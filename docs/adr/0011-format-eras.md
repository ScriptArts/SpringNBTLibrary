# 0011. 形式の世代を選んで1.13以降のワールドを読み書きする

- 状態: 採用
- 日付: 2026-11-20

## 背景

[0003](0003-version-policy.md)は扱える形式の下限より古いデータを読み込みで警告し、書き込みでエラーにすると決めた。
形式が変わったときは下限を上げる。
[0010](0010-palette-format-26-3.md)はこれに従い、26.3でパレットの形式が変わったときに下限を`5006`へ上げ、26.2までの形式を扱わないことにした。

この決め方では、古いバージョンのMinecraftで配布マップを保守している制作者がこのライブラリを使えない。
26.2で作ったワールドを26.3で開いても、読み込まれなかったチャンクは古い形式のまま残るので、26.3のワールドの中にも読めないチャンクが残る。
26.4でも形式が変わる予定で、そのたびに下限を上げると、扱えるワールドが減り続ける。

調べたことと設計は[過去バージョンへの対応の調査](../research/legacy-version-support.md)と[設計](../research/legacy-version-support-design.md)にまとめた。

## 決定

**チャンクとワールドの構成を形式の世代に分け、読んだときの世代のまま読み書きする。** バージョン間の変換はしない。

- 対象は1.13の正式版（DataVersion `1519`）以降とし、`MIN_SUPPORTED_DATA_VERSION`を`1519`に下げる。`TARGET_DATA_VERSION`は`5023`のまま変えない
- チャンクの形式は次の5つの世代に分ける

  | 世代 | DataVersion | バージョン |
  |---|---|---|
  | C1 | 1519〜2202 | 1.13〜1.14.x |
  | C2 | 2203〜2528 | 1.15〜1.15.2 |
  | C3 | 2529〜2843 | 1.16〜1.17.x |
  | C4 | 2844〜5005 | 1.18〜26.2 |
  | C5 | 5006以降 | 26.3以降 |

- ワールドの構成と`level.dat`はL1（DataVersion 4785以下。1.13〜1.21.x）とL2（4786以降。26.1以降）の2つの世代に分ける
- チャンクの世代はチャンク自身の`DataVersion`で決め、構成と`level.dat`の世代は`level.dat`の`DataVersion`で決める。1つのワールドに形式の違うチャンクが混ざりうるためである
- 利用者は`ChunkReadOptions.format_data_version`と`WorldOpenOptions.format_data_version`で、世代を選ぶDataVersionを指定できる。指定できる値は`1519`以上で、それ未満は`INVALID_ARGUMENT`にする
- 書き戻す形式は読んだときの世代で決まり、利用者が書き出す形式を選ぶ手段は設けない。`DataVersion`も書き換えない
- 下限との比較は指定の有無に関わらずチャンク自身の`DataVersion`で行う。
  `1519`未満のチャンクと`DataVersion`の無いチャンクは、どの世代でも解釈せず、元のNBTだけを持つ。
  読み込みは`VersionMismatchAction`に従い、書き込みは`allow_foreign_data_version`で許可しなければ`UNSUPPORTED_DATA_VERSION`にする
- 新しい形式が出たら、下限を上げずに世代を1つ足す
- 世代によって持たない値を扱うAPIは`UNSUPPORTED_FEATURE`にする。1.17までのバイオームは数値のIDで持つので、`get_biome_id` / `set_biome_id`を足し、IDは名前に直さない
- 世代による違いはライブラリの内部に持つ世代の表にまとめる。読み書きのコードは表の値に従い、DataVersionによる分岐をほかの場所に書かない

0003の決定のうち、下限より古いデータを読み込みで警告して書き込みで止めること、`DataVersion`を書き換えないこと、NBTレイヤとAnvilレイヤがバージョンを見ないことは変えない。
0010の決定2〜5はC5のパレットの決め事として残す。

## 理由

- 古いバージョンでワールドを保守している人が、自分のバージョンでも同じコードを使える。世代ごとに別の型を用意すると、利用者が型で場合分けを書く必要がある
- 0010の理由1が挙げた心配には、次のように答える
  - 5言語の分岐: 世代による違いは表の値で表すので、分岐が5言語のあちこちに散らない
  - 書き出す形式の取り違え: 書き出す形式は読んだときの世代で決まり、利用者が選ぶ手段も無いので、取り違えが起きない
  - テスト: 世代ごとに合成のテストベクタを持ち、5言語の出力が一致することを適合性検証で確かめる。
    実ワールドでも、1.13.2から26.3までの各バージョンで、読み込みと無変更での書き戻しがバイト単位で一致することを確かめた（[90 適合性](../spec/90-conformance.md#検証実績)）
- 1.13より前はブロックが数値IDなので、名前への表が要る。ブロックの定義を持たない方針（[0004](0004-defer-heightmap-recalc.md)、0010の決定5）に反するため扱わない
- バイオームの数値IDを名前に直さないのは、1.16.2以降はデータパックで独自のバイオームを足せるので、固定の表では正しく引けないためである
- 指定で世代を上書きしても下限の検査を素通りできないようにしたのは、数値IDのチャンクを1.13以降の世代で読むと、ブロックが1つも無いように見えてしまうためである

## 結果として受け入れること

- バージョン間の変換はできない。古いワールドを新しい形式へ移すのは、これまでどおりMinecraft本体の仕事である
- 世代によって使えるAPIが変わる。
  1.17までの形式では`get_biome` / `set_biome`が、1.18以降の形式では`get_biome_id` / `set_biome_id`が`UNSUPPORTED_FEATURE`になる。
  `isLightOn`の無い1.17までのチャンクでは、`invalidate_lighting`も`UNSUPPORTED_FEATURE`になる
- Rustの公開APIに、互換性の崩れる変更が入る。`ChunkReadOptions`に公開の項目が増え、`clear_heightmaps` / `invalidate_lighting` / `LevelData::spawn_pos`の戻り値の型が変わる
- 開発版（スナップショット）で書かれたチャンクのうち、正式版と形式が違うものは扱わない
- 世代の境界のDataVersionは、実ワールドでは観測したDataVersionの間にあることまでしか確かめていない（[30 7.1](../spec/30-chunk-format.md#71-世代の表)）

# 0002. 命名は各言語のイディオムに従う

- 状態: 採用
- 日付: 2026-08-29

## 背景

「同一機能を全言語で提供する」ことが本ライブラリの存在意義である。
その徹底のしかたとして、メソッド名まで完全に同一にする案があった。

## 決定

**概念・型構成・機能の集合は完全に統一するが、命名は各言語の慣習に従う。**
論理名から各言語名への変換規則を
[spec/00-conventions.md 3章](../spec/00-conventions.md#3-命名変換規則)に定め、
CI の `docs-sync` がその規則で公開APIを論理名へ写して全言語を突き合わせる。

## 理由

- `region_file.ReadChunk()` のような、その言語では明らかに異物な名前は
  利用者の学習コストをむしろ上げる
- 変換規則が機械的である限り、「完全一致」でなくても
  **論理名の集合が一致していることは自動検証できる**。同一性の保証は失われない
- 各言語利用者にとって自然に書けることが、全言語提供の価値を実際に届ける条件になる

## 結果として受け入れること

- 変換規則から外れる名前を付けると CI が落ちる。命名の自由度は下がる
- 言語をまたいで移植する際、名前は機械変換で追える一方、
  ドキュメントには全言語の対応表 (`docs/api/`) が必要になる

## 関連: 基準実装は C#

実装は **C# を基準**として先に書き、他3言語へ移植する。

理由は、設計者が最も慣れている言語だから。
5言語を1人で保守する体制では、**仕様の穴に気づく速さが設計者の習熟度に直結する**。
不慣れな言語を基準にすると、言語と格闘している時間と
仕様を詰めている時間の区別がつかなくなり、判断を誤りやすい。

移植の順序は C# → Java → Python → Rust とする。
C# と Java は型システムが近く差分が小さい。
Rust を最後に置くのは、所有権と網羅的パターンマッチが
「他3言語では通ってしまう曖昧さ」を最後に炙り出す網として働くため。

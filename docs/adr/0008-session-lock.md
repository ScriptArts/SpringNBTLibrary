# 0008. `session.lock`の確認は言語ごとにベストエフォートとする

- 状態: 採用
- 日付: 2026-08-29

## 背景

Minecraftはワールドを開いている間、`<ワールド>/session.lock`を開いたまま排他ロックを保持し続ける。
起動中のワールドに外部から書き込むと、Minecraftがメモリ上に持っているチャンクで上書きされてデータが失われる。

したがって書き込みモードでワールドを開くときは、起動中でないことを確かめたい。

問題は判定方法である。`session.lock`はMinecraftを終了しても残り続けるため、ファイルの存在確認では何も判定できない。
「ロックが取れるか」を試すしか手が無い。

そしてファイルロックは、言語の標準ライブラリで扱えるかどうかが分かれる。

| 言語 | 標準の範囲で排他ロックを試せるか | 手段 |
|---|:--:|---|
| C# | ○ | `FileStream`を`FileShare.None`で開く |
| Java | ○ | `FileChannel.tryLock()` |
| Python | ○（POSIXのみ） | `fcntl.flock`。Windowsには`fcntl`が無い |
| TypeScript | ✕ | Nodeに移植性のあるファイルロックAPIが無い |
| Rust | ✕ | `std`に無い。`fs2`などの外部クレートが要る |

本ライブラリは「1人の開発者が複数言語へ同一挙動のライブラリを提供する」ことを差別化要因に据えている（[0001](0001-monorepo.md)）。
その方針からすると、言語によって挙動が変わるのは望ましくない。

## 選択肢

1. **全言語で確認しない**。挙動は完全に揃うが、C#/Java/Pythonで実現できる安全策をわざわざ捨てることになる。ワールドの破壊は取り返しがつかない
2. **外部依存を足して全言語で確認する**。Rustに`fs2`、TypeScriptにネイティブアドオンが必要。依存を最小限に保つ方針と衝突し、TypeScriptではネイティブビルドが要るため導入の敷居も上がる
3. **できる言語だけ確認し、できない言語は確認しない**。挙動は揃わないが、揃わない箇所と理由が仕様に明記されていれば利用者は判断できる

## 決定

**選択肢3を採る。**

- C# / Java / Python（POSIX）は排他ロックを試し、取れなければ`IO`エラーにする
- TypeScript / Rust / Python（Windows）は**確認しない**
- `WorldOpenOptions.ignore_session_lock`は**全言語に用意する**。
  確認しない言語では効果が無いが、APIの形を揃えるほうが移植時に迷わない
- 確認しない言語では、そのことをオプションのドキュメントコメントに明記する
- [`docs/features.md`](../features.md)では✅と🔶を使い分け、この差異が一覧から読み取れるようにする

## 理由

**「安全を優先する」という考え方は、この件では確認できる言語を優先する方向に働く。**
確認できる言語で確認をやめても、確認できない言語が安全になるわけではない。
一方で確認を残せば、その言語の利用者だけは守られる。
揃えるために安全策を捨てれば、揃えること自体が目的になってしまう。

**誤検出しないことを優先する。** TypeScript版で「`session.lock`が存在するから起動中」と判定すると、終了済みのワールドをすべて拒否してしまい、実用にならない。
判定できないなら、何もしないほうが正しい。

**この差異は隠さない。** 利用者が「TypeScript版でも守られている」と誤解したまま起動中のワールドへ書き込むほうが、「守られていない」と知って自分で確かめるより危険である。

## 結果として受け入れること

- 適合性検証（[spec/90](../spec/90-conformance.md)）はこの挙動を対象にしない。
  ロック状態を再現するテストは環境依存が大きく、言語間diffの題材に向かない
- Rustに`fs2`相当を任意機能（feature）として足す余地は残す。
  そのときも既定は「確認しない」のままとし、有効時のみ挙動が変わる形にする
